# Supabase schema and migrations for FalconBroom

This folder contains SQL to provision core tables and Row-Level Security (RLS) policies for Supabase/Postgres.

Files
- `migrations/0001_init.sql` — creates `teams`, `team_members`, `uploads`, `explanations`, helper functions, and RLS policies.
- `migrations/0002_account_deletion.sql` — adds service-role-only shared-data checking and deletion RPCs. The deletion RPC removes the user's FalconBroom rows and returns their owned Storage objects for deletion through the Storage API; it refuses to modify those rows when it detects shared team data or another person's (or an unknown author's) explanation on an owned upload.
- `migrations/0003_deletion_storage_review.sql` — extends the shared-data check to flag missing or ambiguously owned referenced Storage objects and other users' upload references to the account's objects. Since `uploads.storage_path` does not identify a bucket, matching names across buckets are treated conservatively.
- `migrations/0004_deletion_reservations.sql` — experimental service-role-only account reservations and guards for the four application tables. This is not a deletion service and does not freeze Storage or local desktop writes; do not use a reservation as permission to delete.
- `migrations/0005_reservation_recheck.sql` — rechecks covered shared data on a reservation retry, retaining the reservation if review is required. This does not prevent subsequent Storage writes.
- `functions/delete-account/` — an authenticated, read-only preflight. It checks the signed-in user and password, then reports whether covered shared data was detected. It never deletes data or authorizes deletion.

Test project preparation

Notes & next steps
- The migration assumes Supabase Auth is in use (references `auth.users`). Policies use `auth.uid()` and `auth.role()`.
- Desktop Supabase account deletion remains disabled, including for the disposable test project. The desktop test implementation is gated in code and the deployed experimental Edge Function routes are disabled. Environment variables alone cannot enable the complete destructive flow. A successful preflight is not a reservation or permission to delete anything.
- The preflight authenticates the user, verifies the password with a separate short-lived Supabase session, and calls the shared-data check using server-side privileges. It needs testing against a real test project; it does not yet support the desktop app's cross-origin requests or MFA-specific reauthentication. Do not deploy it for customers.
- The `0002` and `0003` checks only detect sharing represented by the covered tables and Storage object metadata; they cannot identify every form of sharing, bucket access policy, external service, or differently configured database. A preflight does not freeze writes. The experimental `0004` reservation prevents covered application-table changes but not Storage or local writes, and the deletion RPC's guard does not protect subsequent Storage and Auth API calls.
- Storage RLS policies alone are insufficient to freeze all writes: Supabase's [signed-upload implementation](https://github.com/supabase/storage/blob/d0461d8748fc0f8346a25d3743155e15aa3ce091/src/http/routes/object/uploadSignedObject.ts) uses a privileged database connection. A retry recheck cannot prevent another write immediately afterward. Supabase [recommends against altering its Storage schema](https://supabase.com/docs/guides/storage/schema/design); a safe, supported coordination mechanism must be established and tested before enabling deletion.
- Before enabling desktop deletion, implement and test a trusted service with user authentication and reauthentication, durable retry and partial-failure reporting. Check for shared data before deleting local data, prevent new relevant writes throughout deletion, and handle Storage and Auth safely. Review all production tables, Storage ownership, shared-team policy and other data stores. Local files on other devices, backups and exports require separate handling.
- The new queue, worker, authenticated handlers, optional scheduler script, and experimental desktop recovery logic are not an end-to-end deletion service. The destructive handlers are deployed but disabled on the disposable project, the scheduler is not installed, and the atomic operation is not granted to API roles. Desktop acknowledgements are client assertions, not proof of cleanup on other devices or by nonparticipating clients. The opt-in test UI coordinates supported workflow-storage writes with Web Locks and retains a pending marker through recovery; unattributed saved workflow data pauses for review instead of being deleted. In an isolated instrumented Windows build, two app instances shared WebView storage and a workflow lock, and the browser pending/recovery helper blocked and resumed writes with simulated status. A separately instrumented packaged sidecar passed synthetic Source and Join API, cleanup interruption, process restart, recovery, and other-user preservation checks with a mocked cloud. Neither check verifies full end-to-end cleanup through the packaged UI against Supabase, or other app versions; all participating windows must share the same WebView storage origin. The queue retains account identifiers and hashes and requires an explicit retention policy. The desktop release gate remains in place.
- In an isolated instrumented packaged UI with mocked authentication and synthetic files, Source profiling and Join suggestions and preview worked. After those workflows created unattributed browser data, the deletion form reported `browser_review_required` and paused before further local cleanup; synthetic uploads, including another user's upload, remained present. Packaged UI cleanup and recovery were not exercised through completion, and Join export was not tested. The UI also displayed upload metadata files as selectable uploads; that observation has not been investigated.
- A subsequent isolated packaged UI test with account-scoped browser storage produced a Source profile and a two-row Join preview, but deletion paused at `local_review_required` because desktop inspection records had no owner. No local cleanup was performed in that test.
- In a fresh isolated packaged UI with mocked Auth and cloud, Source and Joins worked and five new inspections were attributed to the synthetic owner. An intentionally interrupted deletion removed the target's local uploads and inspections, retained the other synthetic user's upload, and left the pending marker. On restart, the marker blocked `/me`, preventing the UI from reaching the deletion retry. After rebuilding with a fix permitting `GET /me` and its CORS preflight while verifying the pinned test identity and pending owner, the retry reported local cleanup completed; the mock cloud reported completion, the desktop pending marker cleared, and the other user's upload remained. The browser pending warning disappeared, but the individual WebView storage entries were not independently inspected. This is not a Supabase end-to-end test.
- The atomic operation locks Storage metadata only while its transaction runs, not during earlier desktop cleanup or afterward. It cannot prove there are no in-flight object bytes, old signed uploads, or later privileged writes; the never-used-Storage requirement is an external test-project constraint, not something an empty metadata query proves. It also deletes the Auth row directly and does not produce the Auth Admin API's deletion audit entry. Supabase permissions, Auth cascades, Storage behavior and rollback need hosted-project verification before enabling it.
- On 2026-11-12, checks on disposable project `zthtkoekvxplppxanwiu` found no bucket or object metadata and confirmed that `postgres` can read and acquire the required Storage table locks and has Auth-user DELETE privilege. A brief `NOWAIT` lock transaction succeeded and was rolled back. Migrations `0001`–`0008` were applied there in one transaction using explicit-project SQL, then recorded in migration history using the CLI and verified against the exact migration files. The installed deletion functions are owned by `postgres`; the atomic function is not executable by `anon`, `authenticated`, or `service_role`, and rejected a nonexistent job lease. A hosted transaction temporarily granted atomic execution to `service_role`, created synthetic Auth users, deleted one through the queue and atomic operation as `service_role`, verified preservation of the other, and rolled back the data and grant. This was not an Edge Function or PostgREST end-to-end test. Other deletion helper functions are executable by `service_role`, including legacy helpers; protect that key and do not expose those functions. No existing account was deleted. These observations can change as the project changes.
- Browser coordination for the test project is only activated when `VITE_FALCONBROOM_TEST_ACCOUNT_DELETION=1` is set at frontend build time. This does not enable the server or desktop deletion gates; leave it unset in normal builds.
- In the opt-in test build, newly saved workflow history, drafts, and checkpoints use the authenticated test account's ID instead of the legacy global keys. Legacy global data is not automatically attributed or deleted and still requires review. After confirmed local cleanup, account-scoped browser data is removed; a persistent browser marker retries interrupted cleanup, and a per-account tombstone prevents another participating window from recreating it. Switching accounts without restarting pauses the test UI. These safeguards apply only to participating windows sharing the same WebView storage; they do not prove cleanup of other profiles or devices.
- In the opt-in desktop test path, new upload ownership and inspection attribution use the account returned by the pinned test project's Auth user endpoint. An inspection is attributed only when its input has matching owner metadata; a signed-out or unmatched inspection remains unowned. Existing inspection records are not relabeled, and unowned records still block deletion. Existing source metadata is not independently reverified by this change; legacy or otherwise untrusted metadata requires review.
- With the desktop test-deletion flag enabled, join exports are serialized with other desktop requests and are attributed only when the authenticated user owns both input files. Unknown or mixed ownership remains review-only; overwriting an existing output with unverified ownership is rejected. Join history with missing or mismatched source ownership also pauses deletion. Normal builds retain their existing join behavior.
- The disposable Edge Function was deployed with gateway JWT verification disabled so eventual recovery can work after account removal. Its preflight still verifies the bearer token and password, the enabled job routes verify credentials for mutations and a recovery capability for status, and the worker requires its separate secret. The test-only flag and worker secret are currently absent; unauthenticated preflight returned HTTP 401 and the disabled worker returned HTTP 503.
- Supabase `pg_net` temporarily stores decrypted request headers in its request queue. The disposable project's queue is owned by `supabase_admin` and grants all table privileges to `PUBLIC`; both `anon` and `authenticated` have database privileges to read and modify it. A rolled-back attempt by `postgres` to revoke those grants left their access intact. The replacement scheduler avoids this queue entirely: a `pg_cron` job invokes the existing database claim and atomic deletion functions directly, with no worker secret or HTTP request. This removes the scheduler's dependency on `pg_net` confidentiality and integrity; it does not change or secure `pg_net` for other uses.
- Scheduler installation and each invocation reject API-role writes to the cron job or deletion queue, membership in `postgres`, API-role execution of the claim or retry functions, or API/service-role execution of the atomic function. Other database roles, owners, schema privileges, and changes by trusted administrators still require review. Installation requires an explicit session confirmation and the `postgres` role; the confirmation is not proof of the connected project's identity. Verify the target independently. Never install this test scheduler on production. It bypasses the Edge worker and runs as the scheduling database role, so it does not require the atomic operation to be granted to `service_role`.
- `pg_cron` and `pg_net` were installed in the disposable project. A temporary harmless cron job ran successfully and was removed; a separate synthetic `pg_net` request reached the disabled worker and received HTTP 503. The secret-free replacement scheduler was installed and its command executed inside rolled-back hosted transactions with the deletion queue locked and initially empty. The idle command ran as `postgres`; another test created two synthetic Auth rows and a ready job, deleted the target, preserved the other user, and rolled back. No schedule or job persisted. An actual scheduled execution and persistent hosted deletion remain unverified. No deletion schedule or worker secret is installed.
- An empty test project's Storage checks do not prevent an administrator, privileged integration, or signed upload from creating data outside the atomic transaction. Keep production deletion disabled. Do not deploy or test the destructive path until the restricted project's no-Storage assumptions and the atomic operation are verified, and desktop cleanup and recovery have been reviewed end to end.
- Run end-to-end tests in the disposable test project before any production deployment. If migration `0002` was already applied elsewhere, migration tools will not automatically rerun the edited file; a new follow-up migration is required for an existing deployment. The Edge Function was deployed to the disposable project with the destructive routes disabled; no scheduler has been installed.
- The existing non-desktop backend needs `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`; keep the service-role key server-side and never bundle it in the desktop app.
- Local output files referenced by account-owned history must have matching owner metadata before deletion can remove them. If legacy output ownership cannot be verified, account deletion reports a failure and retains the history record for investigation and retry; do not assign ownership based only on a filename.
- Review policies carefully and adapt the role semantics to your product (e.g. add `owner`, `admin`, `member` roles).
- For production, consider adding audit tables and more restrictive policies (and testing with a non-privileged `anon` role).
